# PORTFOLIO.md 維護指南（給 AI 模型）

> 你（AI 模型）被要求更新 [PORTFOLIO.md](PORTFOLIO.md) 時，**只依本指南操作**。
> 本指南的目標：程式碼持續迭代下，任何模型接手都能把作品集更新到與程式碼一致，且風格不走樣。

---

## 0. 這份作品集是什麼、不是什麼

- **是**：對外展示用的履歷 / 作品集文件。讀者是不熟悉本專案的工程師、面試官、合作者。
- **不是**：開發文件（那是 README.md）、規格書（那是 ROADMAP.md）。不要把待辦、bug、內部決策細節搬進來。
- 核心敘事只有一句，改任何段落都不能偏離：**「記一次，前後都有用」——往前是提醒工具，往後是會累積的檔案**。

## 1. 資料來源優先序（衝突時以上面的為準）

1. **README.md 的「更新記錄」章節**——單一真相來源。每筆條目日期式、分「修正 / 新增」。
2. **README.md 其他章節**（功能總覽、專案結構、雲端整合、修改前必讀）
3. **docs/ROADMAP.md**——只用於「八、下一步」
4. **程式碼本身**——只在 README 沒寫清楚時才直接查證（例：某功能是否真的存在）

**絕對規則：不得虛構。** 每一句陳述都要能對應到上述來源之一。找不到依據就不寫，或先問使用者。

## 2. 何時更新

- 使用者明確要求「更新作品集」時；或
- 你剛完成一批功能、已在 README 更新記錄追加條目，且該變更屬於下表任一類型時，順手同步（並在回覆中告知使用者你更新了作品集）。

小型 bug 修正、文案微調、內部重構**不需要**更新作品集——作品集只反映「對外值得講」的變化。

| 變更類型 | 更新章節 | 動作 |
| --- | --- | --- |

## 4. 數據更新指令（更新「七、專案數據」前必跑）

在專案根目錄（Git Bash / POSIX shell）：

```bash
# Kotlin 檔案數
find app/src/main/java -name "*.kt" | wc -l
# 總行數
find app/src/main/java -name "*.kt" -exec cat {} + | wc -l
# UI 模組數
ls app/src/main/java/com/bandary/presentation/ui | wc -l
# 最新版本與日期
git log --format="%ad %s" --date=short | head -3
```

Room schema 版本：查 `BandaryDatabase.kt` 的 `version = N`。行數四捨五入到百位、寫「約 N 行」。同時更新表頭的「數值（YYYY-MM-DD）」日期與「專案摘要」表格中的規模列。

## 5. 寫作規則

- **語言**：繁體中文（台灣用語）。技術名詞保留英文原文。
- **語氣**：遵守 [COPY_GUIDE.md](COPY_GUIDE.md) 的克制路線——自信但不誇大。禁用「革命性」「極致」「完美」「顛覆」；用具體事實代替形容詞（不寫「效能極佳」，寫「單張約 100KB，遠低於 1MiB 上限」）。
- **誠實**：未完成的寫未完成（例：狀態列的「準備上架」在真正上架前不得改成「已上架」）。做過的取捨照實講，「誠實模式」段落就是範例——承認限制反而是加分項。
- **格式**：不加 emoji / icon；章節結構（摘要＋八個編號章節）不得增刪重排，除非使用者明確要求。
- **機密**：**絕不**把 API 金鑰、client id、email、Firebase 專案細節寫進作品集。發現既有內容含機密要主動移除並告知使用者。

## 6. 更新流程（每次照做）

1. 讀 README「更新記錄」中、上次作品集更新日之後的所有條目
2. 依 §3 對照表判斷哪些條目值得反映、動哪些章節
3. 若動到數據 → 跑 §4 指令實測
4. 編輯 PORTFOLIO.md
5. 在本檔案末尾「維護記錄」加一行：日期＋動了哪些章節＋依據哪些 README 條目
6. 在 README「更新記錄」為這次文件更新追加條目（依 README 既有規則）
